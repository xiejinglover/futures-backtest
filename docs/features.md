# 期货回测框架：需求与功能说明

## 1. 目标

构建一个**策略轻、框架重（在适配与执行上）**的期货回测系统：

- **策略层**：只负责计算，并输出**品种层信号**（不关心具体月份合约、换月、费率细节）；
- **框架层**：内置适配与执行能力——加载/转换数据、主力映射、合约路由、换月移仓、撮合记账、绩效统计。

核心要解决的业务问题：

- 研究/信号常基于**主力连续或品种序列**；
- 真实盈亏必须落在**具体月份合约**；
- 换月、手续费、保证金、结算价、涨跌停等机制由框架统一处理，避免每个策略重复实现。

## 2. 非目标

框架**不负责**：

- 内置生产行情库或爬取数据（数据仍在外部；框架通过 Adapter 读取）；
- 实盘下单与券商/CTP 连接（可预留与回测相同的信号接口，但不在本阶段范围）；
- 自动选股/选品种、参数优化平台（可作为上层工具后续扩展）；
- 替用户发明主力认定规则（规则数据由外部提供，框架负责按约定使用，默认 T-1）。

## 3. 设计原则

1. **策略只出信号**：策略面向 `underlying`（品种）工作，输出目标仓位或方向信号即可。
2. **适配与执行在框架内**：主力映射、合约选择、换月移仓、成本与撮合均由框架完成。
3. **框架内部分模块，避免铁板一块**：Adapter / Router / Matcher / Account 职责分离；换数据源只换 Adapter。
4. **信号与成交分离**：连续主力可给策略看；撮合账户只认具体合约。
5. **无未来函数**：策略与路由任一时刻只能使用当时及以前可知的信息；主力默认 T-1。
6. **事件驱动 + 结果可复现**：同样数据源配置 + 策略参数 + 撮合配置 → 输出一致。

```text
│                                   ┌─────────────┐        │
│                                   │   Account   │        │
│                                   │ 持仓/资金    │        │
│                                   └──────┬──────┘        │
│                                          ▼              │

```

**职责一句话**：

| 模块 | 职责 | 策略是否感知 |
|------|------|--------------|
| Adapter | 从外部源读数并转成框架标准结构 | 否 |
| Strategy | 计算并输出品种层信号 | — |
| Router | 信号 → 具体合约订单；换月移仓 | 否（可查只读状态） |
| Matcher | 按 Bar/规则撮合 | 否 |
| Account | 持仓、保证金、盯市 | 策略只看摘要 |
| Performance | 成交、曲线、指标 | 回测结束后查看 |

## 5. 功能需求

### 5.1 策略层（薄）

策略**只做计算与信号输出**，典型接口形态：

```text
on_bar(ctx, bar_view):
    # 可读：品种行情（或框架提供的连续序列视图）、自身信号历史、账户摘要
    # 输出：Signal / TargetPosition
    return TargetPosition(underlying="RB", net_lots=+2)
```

约定：

- 订阅与决策单位是 **`underlying`（品种）**，不是月份合约；
- **不**在策略里写：查主力、拼合约代码、平旧开新、算手续费；
- 可选读取框架提供的「信号行情视图」（如主连/复权连续），该视图**仅用于计算**；
- 需要知道「当前框架正交易哪个合约」时，只能通过 ctx **只读查询**，不能自行改路由。

### 5.2 框架适配层（Adapter）

适配在框架内完成，但**数据仍外置**：

- 框架提供 Adapter 接口 + 至少一种实现（如 `IpquantMysqlAdapter`）；
- 换源时新增 Adapter，不改 Router / Matcher / Strategy API；
- Adapter 负责产出框架内部标准数据（见 5.3），而不是把原始表结构泄漏给策略。

### 5.3 框架内部数据契约

由 Adapter 加载、供 Router/Matcher/Account 使用（策略不直接依赖原始表）：

| 数据 | 作用 | 关键字段（建议） |
|------|------|------------------|
| Bar 行情 | 驱动回测与撮合 | `symbol`, `underlying`, `datetime`, `trading_day`, OHLCV, `open_interest` |
| 信号视图（可选） | 给策略算因子 | 品种连续序列；标注调整方式；**不进入撮合** |
| 合约信息 | 点值、最小跳动、到期 | `symbol`, `multiplier`, `tick_size`, `exchange`, `expire_date` |
| 主力映射 | Router 决定交易谁 | `trading_day`, `underlying`, `dominant_symbol` |
| 费率 / 保证金 | 成本与资金占用 | 按日或按合约 |
| 结算价 | 日终盯市 | `symbol`, `trading_day`, `settle_price` |

说明：

- 调用方配置的是「数据源 + 品种 + 区间」，不是手工拼一堆表塞进引擎；
- 换月事件可由主力映射推导，不必强制外部单独提供；
- `datetime` 与 `trading_day` 分离，明确夜盘归属。

### 5.4 合约路由与换月（Router）

框架必须统一完成：

1. **交易合约解析**：品种在某 `trading_day` 的可交易主力 = 映射表结果（**默认 T-1**）；
2. **信号翻译**：`TargetPosition(underlying, net_lots)` → 针对具体 `symbol` 的开平仓订单；
3. **换月移仓**：主力切换时按配置平旧开新，并计入点差/滑点/手续费；
4. **防未来函数**：默认禁止用 T 日收盘后才确定的主力解释 T 日已发生成交；若提供“研究用宽松模式”，必须显式配置并在结果中标记。

可配置项示例：

- 收盘后切换 / 次日开盘切换；
- 换月日是否仍接受新信号；
- 移仓市价模型、是否分批。

### 5.5 时间与事件推进

- 按时间顺序回放；
- 至少支持：`BAR`、`ROLL`（换月）、`SETTLE`（日终结算）；
- Phase 1 单品种单周期；Phase 2 多品种 / 多周期。

#### 日内主循环（T+0 任意时点开平仓）

`data.bar_freq` 取 `1d / 1m / 5m / 15m / 30m / 1h`，框架**不做重采样**，数据源给
什么周期就回放什么周期。非 `1d` 时每根 bar 都调一次 `on_bar`，策略返回 `None`
表示不动作；要节流请用 `context.bars_seen` 自理。每根 bar 的顺序是：

1. 检验挂单簿，命中即成交；
2. 上一根 bar 留下的市价目标按本 bar 开盘价成交；
3. `on_bar` 决策；
4. 目标变了才撤旧单重挂：市价单等下一根 bar，限价单进挂单簿。

**当日首根 bar 额外做**：今仓滚入昨仓、`next_open` 换月、到期强平。
**当日末根 bar 额外做**：`same_close` 换月、撤光挂单、日终结算。

日线数据每天只有一根 bar，首根即末根，上述顺序退化成原来的开盘段 / 收盘段 / 结算。
结算仍是每交易日恰好一次，`nav.csv` 行数等于交易日数而非 bar 数。

今仓滚入昨仓挂在"该交易日的首根 bar"，而中国期货夜盘属于下一交易日，所以只要数据的
`trading_day` 按交易所口径标注，今昨仓切换点就自动落在夜盘开盘那一刻。这是对数据的
硬要求，见 [data-contract.md](data-contract.md)。

`context.history(freq=...)` 可把原始 bar 聚合成更粗的周期，供"日线出信号、分钟级
执行"的策略使用。周期按交易日而非自然日划分；游标所在的那个周期按已走完的部分返回
——盘中确实知道"今日至此的最高价"，这不是未来函数。

### 5.6 撮合与交易约束（Matcher）

- 限价 / 市价（市价模型可配置：同 bar 收盘、下一 bar 开盘等）；
- 成交价对齐 `tick_size`；
- 涨跌停不可成交；
- 期货开平（开多/开空/平多/平空）；
- 平今/平昨费率差异（数据具备时）；
- 整数手；保证金不足时拒单或缩手数（可配置并记日志）。

#### 限价单语义（挂单簿，存续到收盘）

策略在 `TargetPosition.limit_price` 上给价即为限价单。单根 bar 的判定规则：买单在
`open <= limit` 时按开盘价成交（跳空使挂单立即可成交，价格优势归交易者），否则要求
`low` 按 `execution.limit_fill_rule` 达到限价——`penetrate`（默认）要求击穿，
`touch` 触及即可；卖单对称。限价先对齐到 tick 网格，买单向下、卖单向上取整，保证
对齐后不会比策略要求的更激进。成交的 `slippage_ticks` 记 0。

**委托存续到当日收盘**，逐根 bar 用上述规则检验，由 [book.py](../src/futures_backtest/book.py)
的挂单簿维护。这不是可有可无的：一天一根 bar 时"当日有效"和"当根 bar 有效"重合，
一天 240 根 bar 后二者解耦，若仍每根 bar 撤单就等于**一分钟有效单**，同一策略跑 1m
和 5m 结果不同，且差异来自实现假设而非市场。相应地：

- **同目标不重挂**：新目标与在途的完全相同（净手数与限价都没变）就什么都不做。否则
  持仓目标型策略每根 bar 重发同一目标会把挂单每分钟撤一次重挂，退回一分钟有效单。
- **目标变了撤旧重挂**：净手数或限价任一改变，先撤该品种在途单再挂新的，记
  `reason=superseded`。
- **收盘撤光**：未成交的记 `reason=limit_not_reached`，信号作废不顺延；`same_close`
  换月时会先撤掉旧合约上的在途单，记 `reason=cancelled_on_roll`。不支持跨日 GTC。
- **挂单时即校验保证金**（`execution.check_margin_on_submit`，默认开）：覆盖不了的
  单在提交阶段就以 `insufficient_margin` 拒掉，不进挂单簿。保证金**不冻结**，价格
  大幅不利变动后成交时仍可能不足。

限价只施加于路由到当前主力合约的信号单；换月、到期强平、旧合约残留清理属被迫流量，
挂不上会制造裸敞口，一律市价。`limit_price` 与 `market_fill: same_close` 互斥并在
运行期报错：决策发生在收盘，用同一根 bar 的盘中低点证明成交是未来函数。

一根 bar 的 OHLC 说不出高低点谁先发生。引擎按**距开盘价远近**推断：`open - low <=
high - open` 时假设 开→低→高→收，否则 开→高→低→收。同一根 bar 上多笔委托按该顺序
决定成交先后，这会影响它们争抢同一份可用保证金的次序。

#### 成交量与成交价约束

- 成交价被压回 `[bar.low, bar.high]`。最高价按定义就是该时段最高成交价，买单加滑点
  后超过它的成交若真发生会自己把 high 抬上去。日线罕见，1m 上收在极值是常态。
- `execution.volume_participation` 限制单笔最多吃掉一根 bar 成交量的多少比例，超出
  部分记 `status=partial`，压到 0 手以 `no_liquidity` 拒单。**默认关闭**：它只是
  深度的粗糙替身，猜错比不猜更糟；且它只约束成交量，不表达排队位置。

**已知偏差，读结果时必须知道：**

- **负向选择**：没成交的往往是行情直接跑掉的那批，也就是本该最赚钱的信号。限价单
  回测的胜率与收益天然偏乐观，`skipped_targets` 中 `limit_not_reached` 的占比是
  衡量这一偏差的第一指标。
- **bar 内路径是假设**：nautilus 把同一启发式做成 opt-in 而默认走固定 O→H→L→C，
  说明这个默认值本身可争议；缩短周期只能减轻不能消除。
- **无排队模型**：参与率上限不表达排队位置，`penetrate` 仍是排队失败的粗糙代理。
- **时段跳空**：bar 撮合在有交易时段划分的市场上误差最大，中国期货夜盘与日盘之间
  正是这种断点。
- 不支持止损单（`stop_price`）与跨日 GTC，两者都需要显式的 TIF 字段。
- `events.csv` 行数随 bar 数线性增长，1m 一年约 6 万行。

### 5.7 账户与绩效

- 持仓按**具体合约**记录；策略侧可看品种净敞口摘要；
- 资金：可用、保证金、权益；日终按结算价盯市；
- 输出：成交/委托（含拒单）、换月日志、资金曲线、回撤/夏普/换月成本占比等；
- 可导出 CSV/Parquet。

#### 回合级记录 trades.csv 与两套口径

`fills.csv` 是逐笔流水，`trades.csv` 是回合：按合约与方向维护 FIFO 建仓台账，平仓时
出队配对，给出入场/出场时刻与价格、持仓时长、手数、毛利与分摊手续费。T+0 之后一天
几个来回，"平均持仓多少分钟、单笔盈亏分布"从成交流水拼不出来。指标里对应
`round_trips` / `round_trip_win_rate` / `average_holding_minutes`。

**两者口径不同，不可逐笔相减：** `Account.settle` 每日把 `average_price` 重置为
结算价，所以 `fills.csv` 的 `realized_pnl` 是**结算口径**，只含最后一段，之前各段
落在 `nav.csv` 的 `settlement_variation` 里；`trades.csv` 是**经济口径**，入场到
出场全程。只有 `sum(realized_pnl) + sum(settlement_variation) - sum(commission)`
才等于权益变化。

### 5.8 配置与可复现性

- 配置数据源、品种列表、区间、初始资金、滑点、撮合与换月模式；
- 每次运行生成 `run_id`，记录配置与数据版本摘要；
- 同配置可重复得到一致结果。

## 6. 与「轻引擎」模式的对比（决策说明）

| 方式 | 策略职责 | 框架职责 | 本项目选择 |
|------|----------|----------|------------|
| 轻引擎（更接近开源 vnpy） | 自己指定 `symbol`、自己处理换月 | 主要做撮合记账 | 否 |
| **信号策略 + 框架适配** | 只出品种信号 | Adapter + Router + 撮合全管 | **是** |

选择原因：主力/换月规则应集中维护，避免每个策略重复且不一致；同时保持 Adapter 可替换，避免引擎绑死某一数据库。

## 7. 质量需求（非功能）

| 项 | 要求 |
|----|------|
| 性能 | 单品种多年 1 分钟线可在可接受时间内完成 |
| 内存 | 支持按时间窗/分年流式加载 |
| 扩展 | 新数据源只加 Adapter；新换月规则可配置/可插拔 |
| 测试 | 路由（T-1）、换月、撮合、结算、涨跌停具备单测与黄金样例 |
| 日志 | 拒单、换月、资金不足可追踪 |

## 8. 推荐落地分期

### Phase 1（可用）

- 框架内 Adapter（可先对接 `ipquant` 或本地 mock）；
- 策略只输出品种 `TargetPosition`；
- Router：T-1 主力 + 换月平旧开新；
- 基础撮合、手续费/滑点/保证金；
- 成交、资金曲线、基础绩效。

### Phase 2（增强）

- 多品种组合；
- 信号专用连续序列视图；
- 平今费率、结算盯市细化；
- 涨跌停与流式加载；
- ~~日内多周期回放~~（已完成，见 5.5 日内主循环）。

### Phase 3（可选）

- 与实盘共享同一套信号接口 + Router；
- 参数优化/走步；
- 更精细撮合（盘口、部分成交）；
- 止损单与跨日 GTC（需要显式 TIF 字段）。

## 9. 验收标准（摘要）

1. 策略代码中无需出现具体月份合约选择与换月移仓逻辑，即可完成主连思路的回测。
2. 实际成交与持仓均落在具体月份合约；换月有独立日志与成本。
3. 默认 T-1 主力路由；若启用含未来函数的模式，结果中有明确标记。
4. 替换 Adapter（数据源）不需要改策略代码。
5. 同配置多次运行结果一致。

## 10. 与现有数据的关系（参考）

外部库 `ipquant` 由框架 **Adapter** 读取，**不属于框架仓库内容**：

- 行情：`future_1m_market_data_*`、`future_daily_market_data`
- 主力：`future_dominant_contracts`
- 元数据：`future_contract_info`、`future_all_contracts`
- 成本：`future_charge`、`future_margin_rate`
- 结算：`future_set_price`

框架仓库保留：核心模块、标准契约、Adapter 接口与实现、策略基类、mock 数据与测试。
